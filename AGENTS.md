# Repository Guidelines

## Project Structure & Module Organization

`src/` contains the browser-focused TypeScript library. `src/index.ts` defines
the public export surface, `src/core.ts` provides convenience APIs, and
`src/downloader.ts` owns download and File System Access behavior. Shared types
and defaults live in `src/types.ts` and `src/constants.ts`. Tests are kept in
`tests/` as `*.test.ts`; the declaration fixture verifies consumer-facing types.
`dist/` is generated by tsdown and must not be edited manually. Tooling and CI
configuration live at the repository root and under `.github/`.

## Build, Test, and Development Commands

- `pnpm install --frozen-lockfile` installs the exact locked dependencies.
- `pnpm dev` rebuilds the package in watch mode.
- `pnpm build` emits ESM JavaScript and declarations to `dist/`.
- `pnpm test` runs the Vitest suite once in jsdom.
- `pnpm lint` checks source and tests with Oxlint.
- `pnpm format:check` verifies Oxfmt output; `pnpm format` applies it.
- `pnpm typecheck` runs strict TypeScript checks without emitting files.
- `pnpm release:check:full` performs the complete pre-release validation set.

Use the LTS Node release specified by `.node-version` and pnpm 11 as declared in
`package.json`.

## Coding Style & Naming Conventions

Use two-space indentation, LF line endings, single quotes, no semicolons, and an
80-column target. Oxfmt sorts imports and package metadata; let it handle
mechanical formatting. Use `camelCase` for functions and variables,
`PascalCase` for classes and types, and descriptive kebab-free TypeScript file
names such as `downloader.ts`. Preserve ESM conventions and explicit public
exports. Avoid widening the supported browser targets without discussion.

## Testing Guidelines

Vitest runs in jsdom. Add focused tests beside related coverage using the
`feature.test.ts` pattern and `describe`/`it` wording that states behavior. Test
success, error, abort, callback, and browser-capability paths when changing
download logic. No numeric coverage threshold is enforced, but every behavior
change should have a regression test. Run `pnpm test` and `pnpm typecheck`
before submitting.

## Commit & Pull Request Guidelines

Follow the existing Conventional Commit style: `feat:`, `fix:`, `test:`,
`refactor:`, `build:`, or `chore:`; mark breaking changes with `!`, as in
`feat!: refactor the package`. Keep commits scoped and imperative. Pull requests
should explain the user-visible effect, link relevant issues, list validation
performed, and include screenshots or browser notes when download behavior or
documentation examples change. Ensure all CI checks pass before requesting
review.
